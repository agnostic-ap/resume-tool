# Product Memory

这份文件记录 Resume Tool 的长期产品上下文。Goal 模式每轮先读它，再结合当前代码判断真实状态。

## 产品定位

Resume Tool 是面向求职者和平台方的简历与求职工作台。它不应该只是“编辑简历并导出 PDF”，而应该帮助用户完成：

1. 沉淀职业素材。
2. 创建和维护多份简历。
3. 根据 JD 定制岗位版本。
4. 跟踪投递进度和后续行动。
5. 导出可信、专业、不出错的 PDF。
6. 为平台方和外部系统提供可运营的草稿生成 API。

## 品牌与域名

- 面向中国市场的主域名决策：`jianlistudio.cn`。
- 命名方向：保留 Resume Studio 的产品感，同时用 `jianli` 增强国内用户的搜索语义和记忆点。

## 用户

- 求职者：快速创建、优化、导出不同岗位版本的简历。
- 长期职业规划用户：持续记录项目、指标、技能和成果，之后复用到简历。
- 平台运营 / 超管：管理用户、简历、投递、API 调用、配置和审计。
- 外部系统开发者：通过 API 输入履历和 JD，生成可追踪的简历草稿。

## 当前主路径目标

近期最重要的路径是 C 端求职闭环：

1. 用户选择空白、导入或示例开始。
2. 完成核心字段，并得到明确下一步。
3. 粘贴 JD，生成结构化草稿。
4. 按章节采纳差异，形成岗位版本。
5. 创建关联投递记录。
6. 设置跟进并记录进展。
7. 导出前完成预检，得到稳定 PDF。

## 已知关键风险

- 首次使用仍容易被示例数据撑起来，空白简历引导不足。
- 工作台“AI 定制”承诺和编辑器可见能力不一致；真实 JD 流程曾存在于 `WorkspacePanel.vue`，但入口和呈现需要重新收敛。
- 成长记录如果仍是会重置的 checklist，就不能成为长期职业记忆。
- 投递记录有字段，但还不像机会生命周期管理工具。
- `Saved` 状态不能代表所有对象都已同步成功。
- 导出有页数和分页线提示，但缺少正式预检和修复建议。
- 管理端有视觉框架，但真实数据、认证、权限和动作仍不足。
- 平台 API 有草稿接口，但文档、密钥、配额、审计和契约测试不完整。
- `WorkspacePanel.vue` 承担过多职责，继续扩功能时容易越来越难维护。

## 产品气质

这是一个工作型 SaaS/工具产品。设计要安静、清楚、可信，优先支持反复使用、快速扫描和低错误率。不要把它做成营销 landing page，也不要用大面积装饰去掩盖状态不清晰的问题。

## AI 能力表达

所有 AI 相关体验都要诚实表达：

- 如果只是本地规则或文本建议，不能暗示已经调用真实大模型。
- 如果是 JD 定制草稿，要展示输入、生成状态、失败原因、章节差异、采纳控制和来源追踪。
- `showAI=false` 时，AI 分数、建议、JD 定制入口和相关卡片要遵循同一可见性策略。
