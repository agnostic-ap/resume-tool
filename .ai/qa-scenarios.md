# QA Scenarios

这份文件定义每轮体验改动可复用的验收场景。Goal 模式不需要每次全跑，但要选和本轮改动相关的场景。

## 本地运行参考

C 端前端：

```bash
cd code/front
npm run dev
```

后端：

```bash
cd code/backend
npm run dev
```

管理端：

```bash
cd code/admin
npm run dev
```

测试和构建命令见 `.ai/goal-mode.md`。

## S1. 首次使用和空白简历

用户：第一次使用的求职者。

步骤：

1. 打开 C 端。
2. 选择空白创建。
3. 进入编辑器。
4. 查看是否有明确的下一步和核心字段引导。
5. 尝试填写个人信息、求职标题、简介、最近经历、技能。

期望：

- 不依赖示例数据也知道怎么开始。
- 空章节有主操作。
- 完整度建议指向具体字段或章节。

## S2. JD 定制闭环

用户：正在针对一个岗位改简历的求职者。

步骤：

1. 从工作台点击 AI 定制，或在编辑器内打开 JD 定制。
2. 输入公司、岗位和 JD 正文。
3. 生成草稿。
4. 查看匹配分、关键词、策略、章节 before/after。
5. 采纳一个章节。
6. 创建关联投递记录。

期望：

- 入口承诺和落地能力一致。
- 失败时有错误原因和重试。
- `showAI=false` 时相关 AI UI 一致隐藏。
- 应用后能追踪 request id 或来源元数据。

## S3. 投递生命周期

用户：跟踪岗位进展的求职者。

步骤：

1. 打开投递列表。
2. 新建或打开一个岗位。
3. 查看公司、岗位、阶段、JD、匹配度、联系人、跟进日期。
4. 添加进度事件。
5. 修改阶段或 follow-up 日期。

期望：

- 用户能从待投递推进到 Offer 或关闭。
- 逾期或今日待跟进有明显状态。
- 进度事件可读，后续目标明确。

## S4. 成长记录

用户：希望长期沉淀职业素材的人。

步骤：

1. 打开成长记录页面。
2. 新增一条项目、指标或技能成长。
3. 保存后刷新或切换页面。
4. 再新增另一条。
5. 回看历史记录。

期望：

- 历史不会因为完成 checklist 而丢失。
- 条目包含日期、类型、内容、指标、技能或项目上下文。
- 后续可被 JD 定制选择引用。

## S5. 导出前预检

用户：准备交付 PDF 简历的求职者。

步骤：

1. 填入一份较长简历。
2. 制造一个明显问题：联系方式很长、核心章节为空、经历过多或页面溢出。
3. 点击导出。
4. 查看预检结果。

期望：

- 严重问题不会无提示直接导出。
- 预检给出具体位置和建议。
- 用户可以修复、继续导出或取消。

## S6. 保存和同步失败

用户：担心内容丢失的求职者。

步骤：

1. 启动前端但关闭后端，或制造后端失败。
2. 修改简历、投递或设置。
3. 查看顶部保存状态。
4. 恢复后端后尝试重试。

期望：

- 不显示误导性的单纯 Saved。
- 能区分本地保存、云端同步中、云端失败和离线。
- 失败操作有对象、时间、错误原因和重试入口。

## S7. 管理端平台请求

用户：平台运营 / 超管。

步骤：

1. 打开管理端。
2. 登录或使用本地管理凭据。
3. 查看平台 API 请求日志。
4. 打开请求详情。

期望：

- 数据来自后端，不是静态数组。
- 能看到 client、request id、状态、耗时、失败原因、生成文档 id。
- 危险操作需要确认。

## S8. 响应式和视觉完整性

适用于所有前端 UI 改动。

视口：

- 1280 x 800 桌面。
- 390 x 844 窄屏。

检查：

- 文本没有明显溢出。
- 按钮和控件没有互相遮挡。
- 弹窗、抽屉、侧栏在窄屏可关闭。
- 主操作能被看到并点击。
- 空状态和失败态不是空白。
